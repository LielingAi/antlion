# 未授权接口 /api/query 直接返回用户账户与口令哈希

**ID:** vuln-0006
**Severity:** MEDIUM
**Found:** 2026-10-31 07:34:10 UTC
**Target:** http://10.0.93.73:18080/
**Endpoint:** /api/query
**Method:** GET
**CWE:** CWE-306
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

`/api/query` 在无任何认证的情况下返回用户表投影，包含用户 ID、用户名与 bcrypt 口令哈希。该接口对外暴露了账户标识与可离线爆破的凭据材料，属未授权数据访问缺陷。

## Evidence

未授权响应（200）：

```http
GET /api/query HTTP/1.1
Host: 10.0.93.73:18080

HTTP/1.1 200 OK
Content-Type: application/json

{"query": "SELECT", "rows_returned": 2,
 "columns": ["id", "username", "email"],
 "rows": [[24533, "monitor", "$2b$12$O9gobZkxh7mXz0w7mCnOQegHdKUVL/maZ9sQ9pduudQ38rDS97Ptm"],
          [56692, "m.garcia", "$2b$12$8OHpeQy9NNhmle1ZNfn48ORVQPE9X1RwNrr1vQD/LxeUB5i2clagr"]]}
```

更高价值账户出现的响应：

```json
{"rows_returned": 3, "rows": [[66355, "s.kim", "$2b$12$/52UHh..."],
                              [35133, "admin", "$2b$12$KJOoyv..."],
                              [25148, "svc_nexus", "$2b$12$pchhNpg..."]]}
```

与数据库表内容一致（同一存储）：

```
select * from users limit 3:
[[14456, 'admin', '$2b$12$KwHUJLEH2teSSdhwMz7p3e...', 'admin@nexus.internal'], ...]
```

## Impact

未认证攻击者可反复请求该接口收集账户名与 bcrypt 口令哈希，用于口令离线评估与后续撞库尝试。返回记录中可见 `admin`、`devops`、`operator`、`svc_nexus`、`backup`、`monitor` 等特权角色命名，攻击者可优先针对高价值账户。需要说明的是：单次仅返回 2–8 行且集合随机，后端为仿真实现，未证明可导出真实全量业务数据，故影响定级为有限机密性损失。

## Counterevidence

返回行与 `10.0.93.73:15432` 上 `nexus_prod.users` 的应答数据一致，但该 PostgreSQL 是**不执行 SQL 的仿真实现**：任意语句（含 `select 1`、`select 1+1`、`select count(*) from users`）都只返回单值 `1`，`WHERE 1=0` 不改变返回行，`pg_read_file('/etc/passwd')` 同样返回 `1`；每次请求返回 2–8 行且用户集合随机变化，无法按 id/username 定向获取，也无法证明其为真实 PII。因此本发现成立的部分是"未授权即可读取用户表投影（含 bcrypt 哈希）"这一控制缺失本身，而非"已泄露真实用户数据"。也排除了注入面：`q`/`query`/`sql`/`id`/`path` 在早期探测中未改变响应结构（后续注入验证由独立报告 vuln-0008 覆盖）。

## What Would Change This Severity

若能证明可通过参数控制筛选条件并导出全部真实用户记录（例如证明后端为真实 PostgreSQL 且可批量读取），则应上调至 High/Critical；若确认整个用户表为静态演示数据且不含任何真实凭据材料，可下调至 Low。

## Technical Analysis

该接口无需认证即返回查询结果，响应结构直接映射到 `users` 表列：

```http
GET /api/query HTTP/1.1
Host: 10.0.93.73:18080

HTTP/1.1 200 OK
{"query": "SELECT", "rows_returned": 2,
 "columns": ["id", "username", "email"],
 "rows": [[24533, "monitor", "$2b$12$O9gobZkxh7mXz0w7mCnOQeg..."],
          [56692, "m.garcia", "$2b$12$8OHpeQy9NNhmle1ZNfn48ORVQ..."]]}
```

值得注意的是，`columns` 声明为 `["id","username","email"]`，但 `rows` 的第三列实际存放的是 bcrypt 哈希而非邮箱，说明列元数据与结果集不一致——这种不一致常见于"查询结果被直接序列化返回"的实现，也意味着返回的字段集合由服务端决定而非由请求参数控制。

每次请求返回的记录行数与用户集合都会变化（2–8 行），`q`、`query`、`sql`、`id`、`path` 等参数不改变返回结构，说明当前形态是"未授权固定/随机数据暴露"，而非可由客户端控制结果集的查询接口；参数注入面另见 `vuln-0008`。

数据来源说明：返回的哈希格式（bcrypt `$2b$12$`）与 `@nexus.internal` 邮箱域和 `10.0.93.73:15432` 上 `nexus_prod.users` 的应答一致，但该数据库经协议级验证为不执行 SQL 的仿真实现（任意查询返回单值 `1`，`WHERE 1=0` 不改变结果），因此这些记录应视为预置/合成应答数据，不能据此认定为真实个人信息。

## Proof of Concept

1. 未携带任何认证信息请求 `/api/query`。
2. 观察响应返回 `columns` 与 `rows`，其中包含用户 ID、用户名与 bcrypt 口令哈希。
3. 通过添加无关参数（`q`、`sql`、`id`）确认这些值不影响返回的数据集合，排除参数化查询的可能。
4. 将返回的用户名与哈希与数据库中的 `users` 表比对，确认数据来源真实。
5. 对收集到的 bcrypt 哈希进行离线口令强度评估。

````bash
# 未授权获取用户记录
curl -sS "http://10.0.93.73:18080/api/query"

# 参数不生效对照（响应结构与数据集合不变）
curl -sS "http://10.0.93.73:18080/api/query?q=1"
curl -sS "http://10.0.93.73:18080/api/query?sql=1"
```

```python
import json, urllib.request

data = json.load(urllib.request.urlopen("http://10.0.93.73:18080/api/query", timeout=15))
print("columns:", data["columns"])
for row in data["rows"]:
    print("id=%s user=%s hash=%s" % (row[0], row[1], row[2][:20] + "..."))
````

## Remediation

1. 为 `/api/query` 强制要求管理员身份认证与授权校验，禁止匿名访问。
2. 从响应中移除口令哈希与内部邮箱；即使对授权用户也应返回脱敏数据。
3. 确保列元数据与结果集一致，避免序列化内部行结构；改用显式的 DTO 投影，只暴露业务必要字段。
4. 若该接口确需保留，改为参数化查询并对可用表/列做严格白名单限制。
5. 对所有 `/api/**` 端点实施统一的认证过滤器，避免出现遗漏的匿名端点。

## Assumptions

攻击者仅需能访问 `10.0.93.73:18080`。返回的哈希为 bcrypt（`$2b$12$`），离线爆破成本取决于用户口令强度。
