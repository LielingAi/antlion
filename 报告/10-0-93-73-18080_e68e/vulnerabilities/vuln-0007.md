# Unauthenticated self-declared identity grants authorization level 1 and exposes production credentials

**ID:** vuln-0007
**Severity:** MEDIUM
**Found:** 2026-10-31 07:47:19 UTC
**Target:** http://10.0.93.73:18080/
**Endpoint:** /api/auth
**Method:** GET
**CWE:** CWE-287
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Medium

## Description

The gateway's certification API `/api/auth` grants authorization level 1 to any unauthenticated client that supplies arbitrary `hostname`, `user` and `os` query parameters. No credential, token or proof of identity is required or verified. Level 1 unlocks `/.env.bak` (environment file containing database, Redis, AWS, JWT and Kubernetes credential material), `/debug`, `/actuator/env` and `/api/bounty/submit`. Authorization state is additionally keyed to the client-controlled `User-Agent`, so a new client presenting the same User-Agent string inherits an existing level without registering at all.

## Impact

An unauthenticated network attacker obtains level 1 and reads credential material and internal topology from `/.env.bak` and `/actuator/env`. Protocol-level verification shows that the disclosed PostgreSQL password authenticates as `prod_admin` on `10.0.93.73:15432` (a wrong password is rejected with SQLSTATE `28P01`) and that the Redis password is accepted by `10.0.93.73:16379`, but both services are canned-response implementations: the database does not execute SQL (any statement returns the single value `1`, including `select count(*) from users` and `pg_read_file('/etc/passwd')`), and the cache exposes no data commands or key space. No real business records were retrieved. The disclosed AWS access key is invalid (`InvalidClientTokenId` from STS), the JWT signing secret is not used by any endpoint, and the Kubernetes service-account token and GitLab PAT could not be validated because the referenced internal hosts are unreachable. The demonstrated impact is therefore unauthorized access to the level-1 resource set and disclosure of internal topology and credential material, not confirmed compromise of production data.

## Counterevidence

The level-1 tier is described by the application as free "registration", so one could argue the tier itself is intended to be open. That argument does not neutralize the finding: the tier gates credential material (`/.env.bak`, `/actuator/env`) and the application performs no verification whatsoever of the supplied identity, so "registration" is a self-assertion rather than an authentication step. Levels 2-4 do reject fabricated `user`/`os`/`work_dir`/`env` values, which bounds this issue to the level-1 resource set; `/admin`, `/api/internal` and `/backup` remained 403 and are not claimed here. The strongest constraint is that the disclosed backends are simulated: PostgreSQL authenticates the password (wrong password → `28P01`) but does not execute SQL (every statement returns `1`, a `WHERE 1=0` clause does not change the row set, and `pg_read_file` returns `1`), and Redis accepts `AUTH` but returns `unknown command` for every data command, so no real user records or key space were read. The AWS key is invalid (`InvalidClientTokenId`), the JWT secret is not consumed by any endpoint, and the Kubernetes and GitLab hosts are unreachable, so no lateral movement was demonstrated. What remains fully proven is the authorization defect itself and the disclosure of credential material and internal topology.

## Confidence Rationale

The self-declared level-1 upgrade, its User-Agent binding and the resulting access to `/.env.bak`, `/debug` and `/actuator/env` were reproduced end-to-end against the live target with request/response evidence. The credential material's real-world usefulness is bounded by the simulated backend behaviour documented in the counterevidence.

## What Would Change This Severity

If the level-1 resources are confirmed to contain production credentials that grant access to a real data plane (for example a reachable database, cluster or source-control service holding real business data), this finding should be raised back to High (C:H). Conversely, if the entire level-1 resource set is confirmed to be non-sensitive demonstration data, it would fall to Low.

## Technical Analysis

The gateway implements a four-level "certification" scheme whose state is not bound to any authenticated principal:

**Level assignment is client-asserted.** A fresh client starts at level 0 with only `/api/auth` reachable. A single request containing arbitrary values — e.g. `GET /api/auth?hostname=srv-zx9&user=analyst_zx&os=ubuntu22` — returns `{"level": 1, "status": "UPGRADED", ...}`. No password, token, signature or out-of-band proof is checked. The values are attacker-chosen strings; the server does not compare them against any trusted source before issuing level 1.

**Level 1 unlocks sensitive resources.** After the upgrade, the following change from HTTP 403 to HTTP 200 for the same client: `/.env.bak` (environment file containing the database URL, Redis URL, AWS key pair, JWT secret, Kubernetes service-account token and internal gateway address), `/debug`, `/actuator/env` (plaintext datasource and Redis passwords, AWS access key) and `POST /api/bounty/submit`.

**Authorization state is bound to a client-controlled header.** The server keys the level state to the `User-Agent` string rather than to a session identifier or a credential. A brand-new client that never registered with `User-Agent: curl/8.5.0` immediately reports `"level": 1` and receives `/.env.bak` with HTTP 200, whereas the same request with `User-Agent: curl/8.5.1` reports level 0 and receives HTTP 403. An attacker who knows or guesses another client's User-Agent inherits that client's authorization level. The `sid` cookie (`sid=auto_8216e1609e34b66c`) is static and is not used to bind the level.

Level 2 and above additionally demand environment details (`work_dir`, base64 `env`) and reject fabricated values, so this issue is bounded to the level-1 resource set — which nevertheless contains the credential material above. All HTTP evidence is reproducible without any prior session: the level-1 state is re-established by the same single upgrade request.

Verification of the disclosed material (read-only, protocol level): the PostgreSQL password from `/.env.bak` authenticates successfully as `prod_admin` (an incorrect password yields `FATAL: password authentication failed`, SQLSTATE `28P01`), but the service does not execute SQL — `select 1`, `select 2`, `select 'zzz'`, `select 1+1` and `select count(*) from users` all return the single value `1`, and the returned `users` rows are a fixed canned set that is identical across sessions and unaffected by `WHERE` clauses. The Redis password is accepted (`AUTH` → `+OK`, wrong password → `-WRONGPASS`), while `KEYS`, `SCAN`, `INFO`, `DBSIZE`, `TYPE`, `HGETALL` and `TTL` all return `unknown command` and `GET` returns a nil bulk reply. These results are consistent across two independent PostgreSQL drivers and repeated raw RESP sessions.

## Proof of Concept

1. Send `GET /api/auth` from a fresh client and observe level 0 with only `/api/auth` in `paths`.
2. Request `GET /.env.bak`, `GET /debug?token=abc`, `GET /actuator/env` and `POST /api/bounty/submit`; all return HTTP 403.
3. Request `GET /api/auth?hostname=<any value>&user=<any value>&os=<any value>`; the response is `{"level": 1, "status": "UPGRADED"}`.
4. Repeat the four requests from step 2; they now return HTTP 200 and disclose the production environment, debug topology, datasource secrets and the evidence-submission endpoint.
5. Optional session-confusion check: open a new client with `User-Agent: curl/8.5.0` (previously used by another client) and request `/api/auth` and `/.env.bak` without registering; the client reports level 1 and receives the file, while a different User-Agent remains at level 0 with HTTP 403.

```python
import requests

BASE = "http://10.0.93.73:18080"
H = {"User-Agent": "curl/8.5.1"}

s = requests.Session()
print("before:", s.get(BASE + "/api/auth", headers=H).json()["level"])
for path in ["/.env.bak", "/debug?token=abc", "/actuator/env"]:
    print(path, s.get(BASE + path, headers=H).status_code)

# Self-declared upgrade: arbitrary attacker-chosen values, no credential
r = s.get(BASE + "/api/auth",
          params={"hostname": "srv-zx9", "user": "analyst_zx", "os": "ubuntu22"},
          headers=H)
print("upgrade:", r.json()["level"], r.json()["status"])

for path in ["/.env.bak", "/debug?token=abc", "/actuator/env"]:
    r = s.get(BASE + path, headers=H)
    print(path, r.status_code, len(r.content))

# Authorization state inherits across clients that share a User-Agent
for ua in ["curl/8.5.0", "curl/8.5.1"]:
    fresh = requests.Session()
    lvl = fresh.get(BASE + "/api/auth", headers={"User-Agent": ua}).json()["level"]
    code = fresh.get(BASE + "/.env.bak", headers={"User-Agent": ua}).status_code
    print(ua, "level", lvl, ".env.bak", code)
```

## Remediation

Do not derive authorization level from request parameters. Bind authorization to a server-side session or a cryptographically verified credential (for example a signed token whose issuer, audience and signature are validated) and store the level server-side keyed to that credential, never to the User-Agent or another client-controlled header. Remove production secrets from `/.env.bak` and from actuator environment output, or restrict those endpoints to an authenticated administrative role. Treat "registration" as an authenticated operation requiring a verifiable credential, and default new sessions to the least-privileged level.

## Assumptions

Assumes the attacker can reach the gateway over the network (confirmed). The level-1 resource set is granted without any credential; no pre-existing account or session is needed. The database and cache services accept the disclosed passwords but are canned-response implementations, so the disclosure demonstrates credential material and topology exposure rather than retrieval of real business records.
